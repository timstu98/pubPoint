# Technical designs

Keep one design here for each substantial feature or technical change. A design explains how the agreed product requirements could be implemented and is reviewed before the work starts. Scope it around a capability, such as group membership or venue search, rather than splitting a single user journey into frontend, backend, and database documents. Include all affected layers in the same design when useful.

Each design should state its status (draft, accepted, or superseded), link to the requirements it addresses in the [MVP PRD](../../product/mvp-prd.md), and cover the proposed approach, meaningful alternatives, affected interfaces and data, risks, and how the result will be verified. Name files by capability, for example `group-membership.md`. Small changes can be covered by the issue or PR without a separate design.

Designs record a proposed or agreed approach. Record lasting individual choices in [decision records](../../decisions/). Once a change is built, update the living architecture, API, or database reference where needed; those references describe the current system. Link related documents instead of copying their contents.

The [MVP algorithm plan](../../search-algorithm/mvp.md) is an existing focused design kept with the algorithm research. New general feature designs belong here.
